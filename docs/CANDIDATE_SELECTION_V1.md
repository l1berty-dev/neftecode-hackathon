## Генерация

`generate_candidates(snapshot, policy)` возвращает общий `Action`, без новых
публичных DTO. Для каждого из максимум трёх активных управлений берутся
`current-step`, `current`, `current+step`; строится произведение, максимум 27
системных вариантов **включая baseline**. Значения абсолютные. Неизменённые
значения опускаются из changes; baseline всегда `{}` и всегда первый, даже
если исходный режим вне диапазона или данных недостаточно.

Генератор использует только подтверждённые активные controls со свежим valid
измерением, точной единицей, согласованным возрастом и доступной provenance.
Границы/шаг не подбираются по истории. Для изменённых значений проверяются
диапазон и сетка, привязанная к model_min; Decimal предотвращает ошибки float
modulo, округление к другой уставке не выполняется. На границе диапазона
остаётся до двух вариантов этой координаты. При неподтверждённой/просроченной
координате она не изменяется; это не означает, что baseline допустим.

ID и порядок системных действий детерминированы snapshot ID и отсортированными
signal_id/values; origin/label не входят в выбор. Исходный snapshot неизменен.
Все полученные варианты проходят **тот же ScenarioEvaluator**, включая baseline:
сочетания, ramp limits, применимость, качество и hard checks не заменяются
упрощённой формулой генератора. Rejected и not_assessable исключаются из выбора,
но сохраняются в `Decision.rejected_evaluations` с checks/reasons и в trace.

Действие оператора передаётся в evaluator без изменения payload. Если changes
точно совпадают с непустым системным вариантом, он заменяется операторским,
чтобы не оценивать дубль. В противном случае добавляется ещё один вариант:
максимум 28 вызовов. Пустой операторский action отдельно оценивается, baseline
не заменяется. Отдельная оценка и оценка внутри decide совпадают по содержанию
(кроме нового evaluation_id). Explicit no-op и другие физические дубли не
заполняют список альтернатив; исходные payload сохраняются в trace/оценках.

## Ранжирование и значимость

Сначала обязательные проверки, затем цели: больший будущий выпуск, меньший
статический severity proxy, меньшие будущие затраты. Качество — ограничение
верхней оценки серы <=10 мг/кг, не компенсируемое экономией. Само снижение
точечного прогноза серы не является отдельным основанием изменить режим:
преимущество качества относительно ошибки без модели эффекта не заявляется.
Для устранения недопустимого baseline используется отдельный исход ниже.

`RankingPolicy` — внутренняя конфигурация, не контрактный DTO. Версия сохраняется
в `Decision.explanation`. Для каждой сравниваемой метрики требуется положительный
`threshold`, unit, basis (`predicted` либо `proxy`), evidence и provenance;
для severity — unit `1`, basis `proxy`. Model version обязана совпадать с
версией оценок, provenance доступна не позже snapshot, train-калибровка содержит
train_end и dataset_version. По final test пороги не подбираются. В текущем YAML
нет tolerances: ошибка эффекта ещё не подтверждена, числа не придуманы.

Метрика используется только если **все допустимые варианты** имеют численное
значение с одинаковыми подтверждёнными unit/basis, совпадающими с tolerance.
Это консервативный общий набор координат: если хотя бы один допустимый вариант
неизвестен или несопоставим, координата пропускается для всех. Измеренный текущий
расход не сравнивается с будущим прогнозом. Пропуск и причина отражены в
explanation; unknown не получает ноль или преимущество. Ошибка/область поддержки
самого эффекта должны быть обоснованы перед активацией tolerance; формальный
YAML не доказывает причинность.

При допустимом baseline каждый кандидат сравнивается с ним в порядке целей.
Разница внутри либо ровно на threshold не является доказанным преимуществом.
Первая координата с разницей **строго выше** threshold определяет выигрыш или
проигрыш; значимый проигрыш выпуска нельзя компенсировать следующей целью.
Только выигравшие кандидаты допускаются к change_recommended. Из них выбирается
детерминированный лексикографический минимум по доступным целям, затем меньшему
вмешательству и signal_id/values. Незначимые различия не разрешают действие
сами по себе, даже если используются для стабильного порядка альтернатив.

Вмешательство — сумма `abs(new-current)/step` по изменяемым controls, не сумма
несопоставимых температур/давлений/расходов. Step берётся из подтверждённой
policy. При точном равенстве целевых метрик выбирается меньшее вмешательство,
затем канонический порядок signal_id/values. Origin/label не участвуют.
Выдаются до двух отличающихся допустимых альтернатив; список не дополняется
дублями или неоценёнными вариантами.

## Исходы

- `no_change`: baseline допустим, доказуемого преимущества выше tolerance нет;
  preferred=baseline, даже если другие значения визуально лучше в пределах шума.
- `change_recommended`: есть доказанное модельное преимущество при допустимом
  baseline, либо baseline не прошёл и найден оценённый допустимый вариант.
  Во втором случае выигрыш выпуска не обязателен; это модельное устранение
  нарушения, не аварийная инструкция и не гарантия перехода.
- `insufficient_data`: допустимых вариантов нет и baseline quality сообщает
  insufficient_data для исходного состояния.
- `no_feasible_option`: допустимых вариантов нет по ограничениям/применимости
  либо неизвестным обязательным проверкам; preferred=null. Недопустимый baseline
  не объявляется рекомендацией по умолчанию.

Селектор повторно валидирует контрактные объекты и общую policy: один snapshot,
горизонт и набор версий. Попытка назвать failed/unknown required checks либо
неприменимое качество admissible явно отвергается. Ranking не исправляет
оценки и не обходит pre-model checks, coverage policy или inventory hard checks.
