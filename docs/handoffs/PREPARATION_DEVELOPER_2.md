## Интеграционный интерфейс

```python
from neftecode_hackathon.orchestration import Coordinator
from neftecode_hackathon.reliability import UnavailableReliabilityAgent
from neftecode_hackathon.scenarios import ScenarioEvaluator

evaluator = ScenarioEvaluator(
    quality_agent=quality_agent,  # реальная реализация разработчика 1
    reliability_agent=UnavailableReliabilityAgent(),
    model_version=model_version,  # версия переданной модели
)
decision = Coordinator(evaluator).decide(snapshot, operator_action, horizon_minutes=60)
```

Это намеренно fail-closed каркас. Изменения отклоняются до модели, пока каталог
не утверждён. Проверка `reliability.hard_checks=null` блокирует допустимость даже
baseline с хорошим прогнозом. Индекс тяжести не доказывает выполнение hard checks.
Каркас не умеет рекомендовать изменение или выдавать `no_change`: для этого нужны
этапы B–E, утверждённые проверки и поддержка вмешательств реальной моделью.
Стоимость и будущий выпуск остаются `null/unavailable`, переход не оценён.
Горизонт только 60 минут. Ошибки/отсутствие модели не подменяются числами.

На завершении A файлы YAML фиксировали требования и не загружались как рабочая
политика evaluator. Следующий тогда этап B добавил валидируемый загрузчик каталога
и ограничений, затем механики B–E; не включать `available=true` только ради демо.

## PostgreSQL: команды и транзакции для передачи первому

Локальный постоянный запуск требует собственных значений окружения по `.env.example`.
Пароль в шаблоне не является готовым секретом. Compose читает локальный `.env`,
Alembic требует экспортированный `DATABASE_URL`. В обычном старте нет `create_all`.

```sh
docker compose up -d --wait
uv run alembic upgrade head
uv run alembic check
```

Приложение использует один `Session` и `session.begin()` для `SnapshotRepository.put`
и `DecisionRepository.put`. Репозитории не делают commit сами: вся запись решения
и его оценок должна заканчиваться одной транзакцией до возврата ID клиенту.
Любая ошибка требует rollback. `save(decision_id)` помечает уже рассчитанное решение
и повторно возвращает тот же `saved_at`. Не принимать результаты расчёта от клиента.

Репозитории проверяют конфликты immutable payload по ID. PostgreSQL использует UUID,
TIMESTAMPTZ, JSONB и FK. Прямое изменение данных через SQL вне репозиториев не защищено
DB-триггерами. Схема replay создана; transactional expected_snapshot_id и replay
repository — следующая реализация, не готовая возможность.
Downgrade с удалением истории намеренно запрещён.

```sh
uv run pytest tests/test_developer_2_preparation.py
RUN_POSTGRES_TESTS=1 uv run pytest tests/test_postgres_preparation.py
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

PostgreSQL-тесты opt-in. Создают новый случайно именованный Compose project, случайный
пароль и отдельный порт, выполняют миграцию с нуля. После проверки удаляют только
свой тестовый контейнер/volume. `DATABASE_URL` пользовательской БД не используется.
Обычный pytest пропускает эти два теста; это не означает проверенный PostgreSQL.

Фактически выполнено: Ruff check и format --check всего проекта прошли;
обычный pytest — 24 passed, 2 skipped (PostgreSQL opt-in); отдельный запуск
PostgreSQL — 2 passed. Проверены миграция с нуля, идемпотентность записи/выбора,
FK, rollback, JSON round-trip и чтение после переподключения. Один промежуточный
запуск обнаружил неверное ожидание количества оценок в тесте: общий fixture
содержит две разные оценки, а не одну. Ожидание исправлено по уникальным IDs,
репозиторий не подгонялся под ошибочный тест.
Последний PostgreSQL-прогон дополнительно проверил TIMESTAMPTZ и `alembic check`:
расхождений между ORM и созданной миграцией схемой не найдено.
