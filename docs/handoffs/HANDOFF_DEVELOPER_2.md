## Общий контекст продукта — одинаковый для обоих разработчиков

### Цель и сроки

Команда из двух студентов IT-вуза делает продукт для победы в хакатоне. На разработку — 14 дней. Оба сначала занимаются Python-логикой, затем разработчик 1 завершает API, разработчик 2 делает веб. Не разбивайте работу на изолированные недельные проекты: каждый день интегрируйте текущий общий пример.

Продукт: советчик оператору производства дизельного топлива с интерактивным сравнением действий. Система принимает обновляющиеся измерения, прогнозирует развитие процесса при сохранении управляющих настроек, предлагает предпочтительное изменение и альтернативы. Оператор может ввести своё действие и получить такую же оценку.

Пользователь не должен постоянно загружать таблицы или выбирать исторические даты. В прототипе производственный поток воспроизводится последовательной подачей предоставленной истории. Режим «Воспроизведение истории» видим в UI. Подключение к промышленной системе и исполнение команд оборудованием в эту версию не входят.

Первая предметная область: гидроочистка 24-2000, основной показатель — сера на выходе. АВТ используется как дополнительный контекст сырья. Блендинг остаётся вне v1 без отдельного расширения задачи пользователем; организаторы допускают явно модельный контур и не предоставят дополнительные исходники. Качество после гидроочистки нельзя автоматически объявлять полным соответствием товарного топлива после блендинга.

Ожидаемый результат:
- прогноз сохранения настроек;
- модельная оценка нескольких изменений;
- фильтрация недопустимых вариантов;
- сравнение по качеству, тяжести режима и производственной эффективности;
- объяснение и сохранение решения;
- минималистичный рабочий экран в духе Apple: ясная типографика, спокойные поверхности, минимум лишних шагов.

### Непереговорные правила бизнес-логики

1. Снимок — неизменяемое состояние на момент t, включая доступную к t предысторию. Действие не изменяет исходные измерения.
2. Один цикл сравнения использует один snapshot_id, горизонт и версии модели/ограничений.
3. Пустое действие означает сохранить управляющие настройки. Измерения и качество при этом могут продолжать изменяться.
4. Сценарии — альтернативные следующие действия, не последовательность исполнения друг за другом.
5. Автоматическое и пользовательское одинаковые действия проходят одну функцию оценки и дают одинаковые расчётные результаты.
6. Входы используют только доступные на момент решения сведения. Будущий факт служит целью/проверкой и не попадает в прогноз.
7. ЛИМС — контрольный источник качества, затем ПАК, затем виртуальные анализаторы. Приоритет не означает перенос старого лабораторного значения на настоящее без учёта возраста.
8. Сера <=10 мг/кг — ограничение выбранного модельного сценария на выходе гидроочистки. Это не сертификат полного соответствия товарного топлива.
9. Экономический выигрыш не компенсирует нарушение жёстких ограничений. Текущий режим проверяется наравне с кандидатами.
10. Нет допустимых вариантов — сообщить об этом. Не советовать сохранить режим, если он тоже не прошёл проверки.
11. Неизвестная единица, непроверенное управление или неприменимая модель не превращаются в правдоподобный результат.
12. Показатель тяжести не называется вероятностью аварии. Отсутствие модели перехода к режиму не называется доказательством безопасности перехода.
13. Неподтверждённое влияние действия нельзя выдумывать ради демонстрации. Обученная прогнозная модель сама по себе не доказывает причинность.
14. Искусственные тестовые сбои и тестовые модели явно обозначены; в обычном режиме скрытого fallback на них нет.
15. Нет чата, аккаунтов, микросервисов, автоматического управления оборудованием и LLM-зависимости в критическом расчёте.

### Единые контракты contract_version=1

Владельцем `contracts.py` является разработчик 1; оба сначала согласуют его. Разработчик 2 не заводит альтернативные определения. Изменение контракта сопровождается обновлением общего примера, JSON Schema и теста сериализации.

Имена сигналов используют пространство установки, например `ht:F26`, `avt:T33`. Это примеры идентификаторов, а не подтверждение их управляемости. Лабораторные показатели дополнительно различаются точкой отбора.

| Тип | Обязательное содержание |
|---|---|
| Measurement | value: finite number или null; unit; source; measured_at; available_at; age_seconds; quality: valid/suspect/missing; issues |
| ProcessSnapshot | contract_version; snapshot_id UUID; as_of; mode: replay/manual; dataset_version; values: map сигнал→Measurement; history: записи signal_id/time/value за 6 часов; issues; completeness |
| Action | action_id UUID; label; origin: baseline/system/operator; changes: map signal_id→новое абсолютное значение. Единицы берутся из каталога, не угадываются |
| CheckResult | code; passed: true/false/null; category: data/quality/reliability/control/applicability; message; actual/limit/unit при наличии. null означает «не проверено» |
| MetricEstimate | value или null; unit; basis: measured/predicted/proxy/unavailable; explanation; lower/upper при наличии |
| QualityAssessment | target; forecast_at; prediction; lower/upper; interval_coverage_target; applicability: supported/unsupported/insufficient_data; reasons; model_version |
| ReliabilityAssessment | severity_index или null; factors с вкладом и объяснением; transition_assessed: bool; limitations |
| ScenarioEvaluation | evaluation_id UUID; snapshot_id; horizon_minutes; action; quality; reliability; throughput; cost; checks; admissibility: admissible/rejected/not_assessable; reasons; model_version; constraint_version |
| Decision | decision_id UUID; snapshot_id; horizon_minutes; status: change_recommended/no_change/insufficient_data/no_feasible_option; baseline; preferred или null; alternatives до 2; rejected evaluations; explanation; trace; версии |
| Trace entry | role; input_ids; output summary; check codes. Это журнал расчёта, не искусственная переписка и не скрытые рассуждения LLM |

IDs, origin, label не должны влиять на оценку действия. Сравнение равенства результатов в тестах игнорирует IDs и текстовые названия, но не численные результаты и проверки.

Согласованные интерфейсы:
- `SnapshotProvider.get_snapshot(at) -> ProcessSnapshot` — разработчик 1.
- `QualityAgent.assess(snapshot, action, horizon_minutes) -> QualityAssessment` — разработчик 1.
- `ReliabilityAgent.assess(snapshot, action) -> ReliabilityAssessment` — разработчик 2.
- `ScenarioEvaluator.evaluate(snapshot, action, horizon_minutes) -> ScenarioEvaluation` — разработчик 2; внутри вызывает агента качества и обычные модули проверок/эффективности.
- `Coordinator.decide(snapshot, operator_action=None, horizon_minutes=60) -> Decision` — разработчик 2; пользовательское действие включается в тот же набор кандидатов и может стать preferred.
- `DecisionRepository.save/get/list`, `SnapshotRepository.put/get` — разработчик 2; API использует их через сервисы.

Чистые вычисления не обращаются к PostgreSQL или HTTP. Сервис приложения сохраняет вход и полный результат до возвращения decision_id. Отдельное «Сохранить решение» помечает уже рассчитанное решение как выбранное для истории; оно не принимает произвольный расчёт с клиента.

### Общий HTTP-контракт

Разработчик 1 реализует FastAPI, разработчик 2 потребляет его из React. Базовый префикс `/api/v1`.

| Метод | Запрос | Ответ |
|---|---|---|
| GET /health | — | ready, model_ready, data_ready, database_ready; без секретов |
| GET /controls | — | constraint_version и каталог всех управлений с available, причиной недоступности, единицей, min/max/step, источниками допущений |
| GET /snapshots/current | — | последний снимок и current_snapshot_id |
| GET /snapshots/{id} | — | неизменяемый снимок |
| POST /replay/start | episode_id | снимок и current_snapshot_id |
| POST /replay/advance | expected_snapshot_id | следующий снимок либо 409, если состояние уже изменилось |
| GET /episodes | — | доступные реальные эпизоды, даты и ограничения; synthetic flag для тестовых |
| POST /decisions | snapshot_id, horizon_minutes=60, operator_action=null или changes | Decision и current_snapshot_id, stale |
| POST /scenarios/evaluate | snapshot_id, horizon_minutes=60, changes | ScenarioEvaluation и current_snapshot_id, stale |
| POST /decisions/{id}/save | — | saved=true; повторный вызов идемпотентен |
| GET /decisions?saved_only=true&limit=20 | — | краткая история с IDs, временем и исходом |
| GET /decisions/{id} | — | полный сохранённый расчёт и текущий признак stale |

Отдельный произвольный manual snapshot endpoint не входит в первую версию: ввод оператора — альтернативное действие на реальном снимке. Структура mode оставляет возможность расширения.

Валидация:
- некорректный JSON, неизвестный signal_id, NaN/Inf, неподдерживаемый горизонт → 422;
- несуществующий снимок/решение → 404;
- нет готовых данных или модели → 503, без тестовой подмены;
- известное управление за допустимым диапазоном → HTTP 200 с rejected и причинами, без вызова модели для недопустимого кандидата;
- нехватка данных и отсутствие допустимого решения — нормальные бизнес-ответы HTTP 200;
- ошибки имеют code, message, details.

Сравнение всегда привязано к snapshot_id запроса. stale определяется по current_snapshot_id, не временем получения HTTP-ответа. Устаревшие результаты доступны для просмотра, но явно помечены; перепривязка к новому состоянию требует пересчёта.

Replay в прототипе имеет один общий курсор для одной демонстрационной сессии. В браузере автообновление вызывает advance каждые 5 секунд только после завершения предыдущего шага. Временной шаг данных остаётся 10 минут. Это ускоренное воспроизведение, не промышленная частота опроса. При открытом редактировании альтернативы replay ставится на паузу; внешнее обновление всё равно должно распознаваться как stale.

### Зависимости и точки передачи

1. Совместно: контракты, пример JSON, перечень спорных тегов. Затем оба работают независимо.
2. Разработчик 1 передал реальный SnapshotProvider. Второй использует его вместо fixture в
   production-интеграции; synthetic fixture остаётся только в tests.
3. Разработчик 2 передаёт evaluator/coordinator, работающие с инъекцией тестового QualityAgent. Первый проверяет совместимость реальной модели.
4. Совместно утверждается каталог управлений. До этого механика генерации работает только в tests; реальные советы не считаются готовыми.
5. Разработчик 1 передал continuation model, manifest, QualityAgent и отчёт. Второй подключает
   их без переписывания собственного расчётного пути; action support остаётся отдельной E.
6. Полный цикл проверяется программно; затем первый оформляет API, второй делает UI по OpenAPI и общим примерам.
7. Совместно: запуск на чистом окружении, три демонстрационных эпизода, репетиция.

Не ждать завершения всей чужой подсистемы: ежедневно интегрировать один реальный пример. Тестовые двойники находятся только в tests и не импортируются production-кодом.

### Общие критерии готовности продукта

- Команды подготовки данных, обучения, миграций, запуска API/frontend описаны и воспроизводимы.
- Реальные данные проходят от источника до рекомендации/объяснимого отказа.
- Прогноз сравнивается с persistence baseline, final test не использовался для настройки.
- Действия, для которых нет обоснованной оценки, не получают вымышленных эффектов.
- Исходное состояние и модели сравнения одинаковы для всех вариантов.
- Operator action может стать лучшим; ограничения невозможно обойти.
- Текущий режим проверен, отказ и no_change различаются.
- Постоянные записи работают в PostgreSQL и читаются после перезапуска.
- UI не подменяет актуальное решение поздним ответом.
- Нет зависимости от внешней LLM для вычисления/объяснения.
- Демо: нормальный период; полезное изменение при наличии подтверждённого расчёта; плохие данные/ограничения. Отсутствие обоснованного эпизода полезного изменения фиксируется как незакрытый критерий, не заменяется фальшивой демонстрацией.
- Резервная запись сделана на фактической работе приложения, не на макете.

Если подтверждённых управлений или данных недостаточно, продолжать остальные независимые задачи, запросить уточнение у организаторов и явно перечислить блокированные возможности. Не выдавать прогнозный монитор за полностью завершённый оптимизатор.

### B. Каталог управлений и жёсткие проверки

Каталог обновлён на `ht:P8`, `ht:T11`, `ht:F19`: управляемость подтверждена

В config/controls.yaml для каждого параметра:
- signal_id, русское название, canonical unit;
- verification_status, evidence о смысле и управляемости;
- available и причина недоступности;
- model min/max, step, provenance и явная отметка «экспериментальный диапазон»;
- max_change_per_minute только при подтверждённых данных;
- ограничения совместного изменения.

Проверки выполняются до модели:
1. Все changes относятся к известным разрешённым управлениям.
2. Числа конечны, единицы фиксированы каталогом.
3. Абсолютные значения/шаги/сочетания допустимы.
4. Обязательные данные доступны и свежи.
5. После вызова QualityAgent применимость supported; неопределённость пригодна для выбранной политики.
6. Верхняя оценка серы не превышает 10 мг/кг в принятом модельном сценарии. Отсутствующий интервал не считать проходом.
7. Подтверждённые жёсткие проверки надёжности и перехода выполнены.

Разделить required hard check и informative limitation. Для обязательной проверки passed=null блокирует admissible. Необязательная неизвестная стоимость остаётся limitation, не блокирует автоматически все решения.

Диапазоны нельзя рассчитывать на полном датасете, включая final test. Применять train-диапазоны/экспертные ограничения, полученные совместно с разработчиком 1.

Для известного, но недопустимого управления вернуть rejected и конкретную причину. Не вызывать модель на физически запрещённом кандидате для создания привлекательных чисел.

Исходные требования C ниже сохранены как критерии приёмки.

1. По подтверждённым сигналам выбрать показатели тяжести. Связь с оборудованием описать рядом с формулой.
2. Для каждого фактора хранить текущую/сценарную величину, нормировку, вклад. Если используются исторические нормировки, получать их только из train.

5. Выпуск: отдельно различать текущее измерение и прогноз после действия. Нельзя просто копировать текущий выпуск во все будущие варианты и называть это прогнозом.

7. Затраты: формула по доступным измерениям, подтверждённым единицам и фиксированным допущениям. Нет цен/модели — null, без рублей и процентов экономии.
8. Не превращать «не оценено» в 0 при ранжировании, сериализации или отображении.

Приёмка: оценка содержит факторы/формулы/ограничения, и неустановленный эффект остаётся неизвестным.

оператора, его возможная победа и невозможность обхода hard checks.

После D выполнен E, полный trace отбора и объяснение решения (раздел ниже).
Исходные критерии D ниже сохранены; численная активация реальных действий
по-прежнему требует совместной предметной передачи.

- На каждом из максимум трёх управлений: current-step, current, current+step.
- Построить произведение вариантов, убрать недопустимые и дубли, всегда сохранить baseline. До 27 системных кандидатов плюс действие оператора.
- Все кандидаты идут через один ScenarioEvaluator; никаких отдельных упрощённых формул в подборе.
- Сначала отсеять rejected/not_assessable.
- Достаточный запас качества обеспечивается общей проверкой верхней оценки <=10. Из прошедших сравнивать выпуск, затем меньшую тяжесть, затем затраты, затем величину вмешательства.
- Сравнивать метрику только если она доступна и имеет сопоставимый basis у сравниваемых вариантов. Не ранжировать прогноз против неизвестного значения как будто неизвестное равно нулю.
- Значимость изменения: для качества выигрыш должен превышать сопоставимую оценку ошибки; для прочих показателей — документированный model tolerance. Если погрешность эффекта неизвестна, не объявлять этот эффект доказанным преимуществом.
- Если baseline допустим и нет доказуемого преимущества, status=no_change, preferred=baseline.
- Если baseline недопустим, но есть оценённый допустимый кандидат, его можно рекомендовать для устранения модельного нарушения независимо от выигрыша в выпуске. Не выдавать это за аварийную инструкцию.
- Если входных данных недостаточно для самого состояния, status=insufficient_data.
- Если данных достаточно, но ни один вариант не прошёл, status=no_feasible_option, preferred=null. Baseline может находиться среди rejected.
- При равенстве выбирать меньшее вмешательство, затем детерминированный порядок по signal_id/values.
- Вернуть до двух отличающихся альтернатив; не заполнять список дублями.
- Сохранять причины отклонения, включая «не удалось оценить», а не только найденные нарушения.

Пользовательский вариант включать в decide на равных. origin/label не влияют на выбор. Функция отдельной оценки пользовательского действия и оценка внутри decide должны совпадать.

### E. Координатор и объяснения

Статус на 2026-09-15: технический E выполнен. Coordinator реализует один
детерминированный конечный цикл, baseline перед генерацией остальных actions.
`orchestration/explanation.py` строит текст только из вычисленных фактов:
исход/проблема, настройки и свежесть, прогнозы/unknown с unit/basis, проверки,
основание выбора, альтернативы и ограничения. Unknown не подменяется нулём,
transition flag не представляется гарантией; action model E первого всё ещё нужен.

Trace содержит реальные validation/generation/evaluator/selection с ID-связями,
результатами и причинами, не вымышленный диалог. Все evaluations представлены,
включая допустимые варианты вне двух альтернатив. Контракт/fixture/schema
и БД не менялись. 9 новых E-тестов; общий pytest 172 passed, 2 skipped,
Ruff check/format --check прошли. Реальный smoke/миграции не запускались.
Передача первому: интерфейсы, зависимости, пример композиции, воспроизводимый
synthetic результат и тесты в [COORDINATOR_V1.md](../COORDINATOR_V1.md).

Следующий собственный этап — F, полнота repositories/replay persistence и
проверки на отдельном PostgreSQL. Исходные критерии E ниже сохранены.

Цикл:
1. Проверить состояние и конфигурацию.
2. Оценить baseline.
3. Получить кандидаты + operator action.
4. Вызвать качество, надёжность, эффективность и hard checks.
5. Отобрать/ранжировать.
6. Сформировать Decision и trace.

Первую версию сделать детерминированной без бесконечных раундов «обсуждения». Текста достаточно из шаблонов по вычисленным фактам:
- проблема/возможность;
- какое управление: текущее → предлагаемое;
- ожидаемые эффекты и их basis;
- какие ограничения выполнены;
- почему предпочтительнее альтернативы;
- что неизвестно.

Объяснение не добавляет чисел, которых нет в evaluations. Ограничения/отказы всегда конкретны. Вывод координатора не может исправить rejected в admissible.

Передача первому: evaluator/coordinator, список зависимостей, tests и пример результата. Он подключает к API, не копирует реализацию.

### F. PostgreSQL и repositories

Использовать PostgreSQL с фиксированным major image (postgres:17), именованным volume и healthcheck. SQLAlchemy 2 + psycopg; Alembic — единственный путь создания/изменения схемы. Не полагаться на create_all при обычном старте.

Начальная схема:
- snapshots: id UUID PK, as_of TIMESTAMPTZ, mode, dataset_version, payload JSONB, created_at;
- decisions: id UUID PK, snapshot_id FK, status, horizon_minutes, model_version, constraint_version, payload JSONB, saved_at nullable, created_at;
- scenario_evaluations: id UUID PK, snapshot_id FK, decision_id nullable FK, action JSONB, payload JSONB, created_at;
- replay_state: фиксированная строка локальной сессии, episode_id, current_snapshot_id FK, position.

Структурированные индексируемые поля + полные payload обеспечивают читаемую историю и воспроизведение; не дробить каждый отсчёт истории на множество таблиц v1.

- Снимки/evaluations immutable.
- Расчётное решение и связанные оценки сохранять одной транзакцией.
- save(decision_id) выставляет saved_at и идемпотентен; клиент не может прислать произвольные «результаты агентов» для сохранения.
- Репозитории принимают/возвращают контрактные модели.
- Replay advance проверяет expected_snapshot_id в транзакции, чтобы два запроса не пропускали состояние.
- Все ORM/SQL-запросы параметризованы.
- При недоступной БД API сообщает ошибку; сохранение не имитируется browser storage.
- Полный исходный поток остаётся Parquet; в snapshots сохраняются состояния, участвовавшие в работе продукта.
- .env.example содержит DATABASE_URL template, пути данных/модели и локальные порты; реальные credentials игнорируются Git.

Интеграционные тесты прогонять на отдельной PostgreSQL database/schema, никогда не удалять пользовательскую историю при setup/teardown. Проверить миграцию с нуля, транзакцию, FK, round-trip timezone/JSON, идемпотентность save и чтение после reconnect.

### G. Frontend после работающего общего расчёта

Стек React + TypeScript + Vite. Получить OpenAPI от первого разработчика; генерировать типы, не поддерживать вручную вторую несовместимую копию схемы. Использовать один API client.

Один основной экран:
1. Верхняя строка: «Гидроочистка 24-2000», replay-статус, момент состояния, запуск/пауза.
2. Карточка Decision: ясный исход, действие и причина; состояния загрузки/ошибки/отказа/no_change различаются.
3. Качество: история измерений, порог 10, прогнозная точка на t+60 и интервал. Между t и t+60 не рисовать неподтверждённую траекторию.
4. Сравнение: baseline, preferred, operator; при наличии альтернатив их можно выбирать вместо operator-колонки для просмотра. Одинаковые единицы, horizon и snapshot.
5. «Проверить своё изменение»: numeric inputs по /controls, текущее значение, min/max/step, reset. Недоступное управление с причиной.
6. Действие «Сравнить и пересчитать совет» вызывает /decisions с operator_action, чтобы вариант оператора мог стать лучшим. Отдельная проверка использует /scenarios/evaluate.
7. Раскрываемые блоки: проверки, факторы надёжности, источники/свежесть, trace.
8. «Сохранить решение» и компактная история сохранённых решений.

UX:
- Минимализм не скрывает единицы, свежесть, неизвестные эффекты и существенные предупреждения.
- Сравнение обновляется атомарно, а не отдельными числами от разных состояний.
- Редактирование замораживает текущий snapshot и приостанавливает свой replay.
- При внешнем обновлении показывать «Исходное состояние изменилось» и кнопку пересчитать на новом снимке.
- Использовать AbortController и счётчик/ключ запроса snapshot_id+action+horizon. Abort сам по себе не гарантирует порядок; ответ устаревшего поколения игнорируется.
- Пока запрос выполняется, не отправлять дубли автоматически; кнопка save защищена от повторов, сервер всё равно идемпотентен.
- Прогноз/proxy/не оценено явно различимы. Нет произвольного confidence 95% без данных модели.
- Поддержать клавиатуру, подписи input, читаемые цвета/шрифты, пустые/ошибочные состояния и узкий экран.
- История решения открывается с его исходным snapshot, не с текущими измерениями.
- Зависимость от внешнего LLM отсутствует.

До готовности API допустимы fixture responses для UI-разработки, но mock mode имеет заметную маркировку и не включён по умолчанию в финальной сборке.

### H. Тесты и финальная передача

Unit:
- no-op action;
- неизвестное/запрещённое управление;
- границы и комбинации;
- null/NaN и unknown check;
- throughput не компенсирует качество;
- baseline rejected не превращается в no_change;
- одинаковый action system/operator даёт одинаковые оценки;
- пользовательский action может стать preferred;
- нет значимого улучшения → no_change;
- все недопустимы → no_feasible_option;
- недостаточные данные → insufficient_data;
- unknown cost не равно 0;
- repeatability и предел числа кандидатов.

Frontend:
- поздний ответ для старого snapshot/старой правки игнорируется;
- при смене снимка сравнение не смешивает значения;
- ошибка API не выглядит как отказ по технологии;
- unavailable metric отображается «не оценено»;
- save использует ID реального решения;
- график показывает только поддерживаемый прогноз.

Совместный E2E:
- PostgreSQL migrations → реальный snapshot → решение → operator action → сохранение → чтение истории;
- нормальный эпизод, эпизод изменения, искусственно испорченные данные с явной маркировкой;
- сборка frontend и запуск в чистом окружении;
- запись фактической демонстрации.
