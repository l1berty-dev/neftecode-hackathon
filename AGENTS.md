# Инструкции для работы в репозитории

## Продукт и границы первой версии

Создаём советчик оператору производства дизельного топлива с интерактивным
сравнением сценариев. Система получает обновляющиеся измерения, прогнозирует
сохранение текущих настроек, оценивает возможные изменения и объясняет выбор.
Оператор может предложить своё действие; оно оценивается наравне с системными.

- Первый контур: гидроочистка 24-2000, основной показатель — сера на выходе.
  АВТ — дополнительный контекст сырья.
- В прототипе поток воспроизводится из истории. Явно показывать режим replay;
  не представлять его как подключение к реальному производству.
- Блендинг, промышленное исполнение команд, аккаунты и чат не входят в первую
  версию без расширения задачи пользователем.
- Система рекомендует, но не управляет оборудованием. Показатель тяжести режима
  не равен вероятности аварии или остаточному ресурсу катализатора.
- Сначала интегрировать Python-логику, затем подключать API и веб. Предпочитать
  небольшой проверяемый полный цикл набору несвязанных моделей и экранов.

## Что читать перед изменениями

1. Проверить `git status --short` и релевантный diff. В репозитории могут
   одновременно работать два разработчика; сохранить их незавершённые изменения.
2. Прочитать подходящий handoff:
   - `docs/handoffs/HANDOFF_DEVELOPER_1.md`: данные, качество, FastAPI.
   - `docs/handoffs/HANDOFF_DEVELOPER_2.md`: сценарии, надёжность, PostgreSQL, React.
3. Для интеграции прочитать `docs/CONTRACT_V1.md`,
   `src/neftecode_hackathon/contracts.py`,
   `src/neftecode_hackathon/quality/base.py` и `config/model.yaml`.
4. Для предметных решений сверяться с `context/ТЗ_нефтекод.pdf`, справочником
   `context/Теги_хакатон.xlsx`, схемами и соответствующими исходными данными.

Текущее состояние реализации определять по коду, тестам и конфигурации: разделы
handoff о состоянии репозитория могут устареть. Исполняемый контракт находится
в `contracts.py`; не создавать параллельные DTO. Несоответствие требованиям
исправлять согласованным изменением кода и документации, а не молчаливой подменой.
При изменении общих договорённостей обновлять общий раздел обоих handoff.

## Стек и структура

- Python + FastAPI + Pydantic; окружение и зависимости через `uv`.
- pandas/numpy, openpyxl для чтения Excel, pyarrow/Parquet, scikit-learn/joblib.
- PostgreSQL + SQLAlchemy + psycopg; миграции Alembic. Не заменять PostgreSQL
  на SQLite, в том числе в интеграционных тестах.
- React + TypeScript + Vite; frontend работает через API, без расчёта
  производственных метрик и прямого доступа к БД.
- PostgreSQL хранит снимки, действия, оценки и решения. Подготовленные ряды —
  `data/processed/`, модели и отчёты — `artifacts/`.
- Версию Python и доступные команды проверять по `pyproject.toml`,
  `.python-version`, lock-файлам и реализации. Не объявлять запланированные
  команды работающими до их реализации и проверки.
- Секреты — только через окружение. `.env.example` содержит безопасные примеры.
  Не добавлять секреты, большие производные данные и бинарные модели в Git.

## Архитектура и контракты

Основные типы: `ProcessSnapshot`, `Action`, `ScenarioEvaluation`, `Decision`.
Детали полей и enum брать из `contracts.py`.

- `QualityAgent.assess(snapshot, action, horizon_minutes)` оценивает качество.
- `ReliabilityAgent.assess(snapshot, action)` оценивает тяжесть и ограничения.
- `ScenarioEvaluator.evaluate(snapshot, action, horizon_minutes)` — общий путь
  оценки системного и пользовательского действия.
- `Coordinator.decide(...)` организует вызовы, отбор и объяснение.
- Загрузчики, проверки, расчёт эффективности и сохранение — обычные модули.
  Не создавать дополнительные агенты или сервисы без конкретной необходимости.
- Чистые вычисления не обращаются к HTTP или PostgreSQL. Зависимости агентов
  передавать явно; тестовые двойники размещать в `tests/`.
- Production-код не импортирует тестовые модели и не подменяет отсутствующие
  артефакты синтетическим результатом. Отсутствие модели должно быть явным.
- LLM не требуется в критическом пути. Объяснение строится из вычисленных
  фактов; trace содержит вызовы, результаты и причины, а не вымышленный диалог.
- При изменении контракта одновременно обновлять fixture, JSON Schema,
  документацию и тесты. Frontend не должен иметь независимую трактовку схемы.

## Правила данных и обучения

- `context/` — неизменяемые исходники. Исправления делать в преобразованиях,
  сохранять происхождение, исходную единицу и причину исправления.
- Синхронизировать источники только по времени. ЛИМС содержит независимые пары
  дата–значение; ПАК содержит разные серии в A:B и D:E.
- Различать установки и точки анализа: `ht:`, `avt:`, лабораторные point IDs.
  Буква в коротком теге не доказывает физический смысл или управляемость.
- Проверять соответствия справочника и единицы. Не считать все значения 307
  ошибкой, не превращать `Pt Created`, пропуск или неизвестный показатель в ноль.
- ЛИМС — контрольный источник, затем ПАК, затем виртуальный анализатор.
  Всегда учитывать свежесть; старый анализ не становится текущим фактом.
- Хранить `measured_at` и `available_at`. В snapshot на t допускается только
  информация, измеренная и доступная не позже t. Запретить backfill из будущего.
- Часовой пояс исходников без offset, задержки и свежесть брать из конфигурации
  и обозначать как допущения. Внутреннее хранение UTC; отображение Europe/Moscow.
- Начальные настройки: прогноз 60 минут, история 360 минут. Другой горизонт
  нельзя обслуживать той же моделью без подтверждённой поддержки.
- Разделять train/validation/test по времени, исключать пересечение target
  интервалов на границах. Fit преобразований только на train; test не использовать
  для настройки модели, диапазонов или выбора признаков.
- Один feature builder для обучения и inference. Проверять модель относительно
  прогноза последнего доступного значения; показывать проигрыш, если он есть.
- Отдельно измерять качество относительно ПАК и ЛИМС. Метрики сопровождать
  объёмом выборки; отсутствие событий не выдавать за нулевую долю ошибок.
- Версионировать данные, конфигурацию, модель и ограничения. Replay не должен
  использовать модель, при обучении или подборе которой было доступно его будущее.

## Правила рекомендаций

- Snapshot неизменяем. Action задаёт новые абсолютные значения разрешённых
  управлений. Пустой `changes` — сохранить настройки, а не заморозить процесс.
- Все альтернативы сравниваются от одного `snapshot_id`, на одном горизонте
  и с одинаковыми версиями модели/ограничений.
- Один и тот же action получает одинаковую оценку независимо от origin/label.
  Вариант оператора может стать предпочтительным.
- Допускать только подтверждённые управления. Исторические min/max — модельные
  диапазоны, не промышленные пределы. Фиксировать источник каждого ограничения.
- Прогноз продолжения процесса не доказывает эффект вмешательства. Для действия
  проверять применимость и совместную поддержку условий, неизменность предыстории
  и обоснованность изменения признаков. Неподдерживаемый сценарий не оценивать
  фиктивными числами.
- Сера <=10 мг/кг — ограничение выбранного сценария на выходе гидроочистки,
  не доказательство полного соответствия товарной спецификации после смешения.
- Сначала проверять жёсткие ограничения, затем ранжировать допустимые варианты.
  Производительность или экономия не компенсируют нарушение качества.
- Неизвестная обязательная проверка не считается пройденной. Неизвестная
  стоимость остаётся «не оценено», а не нулём или автоматическим выигрышем.
- Проверять baseline наравне с остальными. Если он тоже недопустим, нельзя
  рекомендовать его только потому, что других вариантов нет.
- Различать `change_recommended`, `no_change`, `insufficient_data`,
  `no_feasible_option`. Давать конкретную причину каждого исхода.
- Не предлагать изменение ради шума: преимущество должно быть значимо с учётом
  неопределённости. Не обещать точную экономию без модели и исходных данных.
- Допустимое конечное значение не доказывает безопасность перехода к нему.
  Подтверждённые ограничения скорости проверять; отсутствие оценки перехода
  явно указывать.

## API, PostgreSQL и интерфейс

- Детали маршрутов брать из общего HTTP-контракта handoff и актуального OpenAPI;
  не создавать второй API для frontend.
- Снимки и результаты сохранять с версиями. Сохранение выбранного решения
  идемпотентно и работает по серверному decision_id, не по расчётам клиента.
- Миграции через Alembic; не заменять ими пользовательскую БД с удалением истории.
  Секреты и SQL не выводить в пользовательские ошибки; запросы параметризовать.
- Сравнение закреплено за снимком. При новом состоянии показывать устаревание
  и пересчитывать явно; поздний ответ не должен затирать свежий результат.
- Редактирование альтернативы приостанавливает локальный replay. Учитывать
  внешнее обновление; одного AbortController недостаточно для защиты от гонок.
- UI: состояние, совет, сравнение, ввод действия, объяснение и сохранение.
  Единицы, свежесть, ограничения и «не оценено» не скрывать ради минимализма.
- Показывать только рассчитанные прогнозы. Если модель предсказывает точку
  через час, не рисовать вымышленную динамическую траекторию.
- Не публиковать приложение или производственные данные по собственной инициативе.

## Параллельная работа

| Ответственность | Разработчик |
|---|---|
| Контракты, данные, quality, API, CLI, модельная конфигурация | 1 |
| Сценарии, reliability, optimization, orchestration, persistence | 2 |
| PostgreSQL/Compose/Alembic, frontend, каталог управлений/ограничений | 2 |
| pyproject.toml, uv.lock, .python-version, сборка корневого README | 1 |

Это границы координации, а не повод блокировать явно порученную задачу.
Согласовывать изменения общих файлов, не дублировать отсутствующий чужой модуль.
При параллельной работе использовать интерфейс и явно тестовый двойник.
Регулярно интегрировать один сквозной пример до завершения всех подсистем.
Самостоятельно не запускать дополнительных агентов без запроса пользователя.

## Проверки перед завершением

Для изменения Python выполнить релевантные тесты и проверки затронутых файлов;
перед общей интеграцией:

```sh
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

После согласованного изменения контрактов:

```sh
uv run python scripts/export_contract_schema.py
uv run pytest tests/test_contracts.py
```

Команда экспорта изменяет генерируемую схему: проверить diff и включить её
в изменение вместе с fixture. Не запускать исправляющее форматирование всего
проекта поверх чужой незавершённой работы.

- После появления frontend выполнять его typecheck, тесты и build согласно
  package.json. Не придумывать команды, которых ещё нет.
- PostgreSQL проверять на отдельной тестовой БД: миграции с нуля, транзакции,
  сериализация, идемпотентное сохранение, чтение после повторного подключения.
- Обязательные сценарии: отсутствие временной утечки; равенство оценки action
  разных origin; невозможность обхода hard checks; корректный отказ;
  недопустимый baseline; защита от устаревших ответов; полный путь до сохранения.
- Для изменения только документации проверить ссылки и согласованность;
  обучение модели и полный тестовый набор без необходимости не запускать.
- В результате работы кратко сообщить, что изменено, что реально проверено
  и какие ограничения остаются. Не объявлять mock, непроверенную модель или
  незапущенную миграцию готовым продуктом.
